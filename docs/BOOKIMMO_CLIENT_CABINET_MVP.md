# Bookimmo Client Cabinet MVP

## Цель MVP

Сделать первый рабочий кабинет клиентов `bookimmo`, в котором арендатор может:

- зарегистрироваться и войти;
- заполнить максимально полный профиль;
- искать объекты на карте и списком;
- сохранять фильтры и избранное;
- размещать заявку на аренду;
- видеть статус своих заявок;
- получать базовую прозрачность по процессу.

MVP должен быть достаточно простым, чтобы быстро запустить, но достаточно структурным, чтобы потом не переделывать архитектуру с нуля.

## Ключевые роли

### Клиент

Основной пользователь кабинета.

Что делает:

- создает аккаунт;
- заполняет профиль;
- настраивает критерии поиска;
- отправляет заявки;
- следит за статусами;
- управляет документами и предпочтениями.

### Оператор Bookimmo

Внутренний пользователь.

Что делает:

- видит заявки клиентов;
- может проверять полноту профиля;
- связывает клиентов с объектами;
- при необходимости запускает internal automation.

### Администратор

Нужен не в первом интерфейсном MVP, но в архитектуре стоит учитывать.

## MVP-экраны

## 1. Sign Up / Log In / Reset Password

Основа уже частично есть в проекте.

Минимум для MVP:

- регистрация по email/password;
- вход;
- reset password;
- подтверждение email;
- базовый onboarding после первой регистрации.

После первого логина:

- если профиль пустой, пользователь попадает в flow заполнения профиля;
- если профиль уже есть, попадает в кабинет.

## 2. Dashboard

Главный экран после входа.

Что должен показывать:

- приветствие;
- прогресс заполнения профиля в процентах;
- количество активных заявок;
- количество сохранённых объектов;
- количество сохранённых поисков;
- ближайшие действия:
  - дозаполнить профиль;
  - загрузить документы;
  - завершить заявку;
  - посмотреть новые подходящие объекты.

Основная задача dashboard:

- не быть перегруженным;
- быстро приводить пользователя к действию.

## 3. Profile

Это центральный экран MVP.

Нужно сделать профиль не “формальностью”, а активом для конверсии.

Разделы профиля:

- Personal
  - имя, фамилия, дата рождения, гражданство;
  - семейное положение;
  - состав семьи;
  - количество детей;
  - домашние животные;
  - курение.
- Contact
  - email;
  - телефон;
  - предпочитаемый язык;
  - текущий город;
  - страна проживания.
- Rental Intent
  - цель аренды;
  - желаемый город/районы;
  - бюджет;
  - желаемое количество комнат;
  - срок заезда;
  - срок аренды;
  - тип объекта.
- Employment & Finance
  - статус занятости;
  - работодатель;
  - ежемесячный net income;
  - источник дохода;
  - есть ли поручитель;
  - кредитная история / SCHUFA availability.
- Housing Situation
  - текущий статус жилья;
  - причина переезда;
  - срок освобождения текущего жилья.
- Documents
  - ID/passport;
  - proof of income;
  - SCHUFA;
  - employment confirmation;
  - cover letter / intro.
- About Me
  - текстовая самопрезентация;
  - предпочтительный текст для заявок.

Нужные UX-механики:

- completion score;
- подсказки, чего не хватает;
- “strong profile” badges;
- autosave;
- editable sections, а не одна огромная форма.

## 4. Search

Этот экран уже существует как страница проекта, его логично эволюционировать.

Минимум для MVP:

- список объектов;
- фильтры;
- карта;
- переключение `Map / List`;
- карточка объекта;
- сохранение в избранное;
- создание заявки из карточки.

Фильтры MVP:

- город;
- районы;
- бюджет min/max;
- комнатность;
- тип объекта;
- площадь;
- furnished / unfurnished;
- pets allowed;
- move-in date;
- listing type.

Поведение:

- при изменении фильтров карта и список синхронно обновляются;
- текущий фильтр можно сохранить как saved search.

## 5. Property Details

Нужен отдельный экран объекта.

Что показываем:

- фото;
- цена;
- адрес или район;
- карта;
- характеристики;
- описание;
- доступность;
- статус “подходит вам / профиль неполный / сначала дозаполните профиль”;
- CTA:
  - `Save`;
  - `Apply`;
  - `Share`.

Важно:

- если профиль пользователя неполный, система должна мягко доводить до заполнения, а не просто блокировать.

## 6. Rental Request / Application Flow

Это не просто кнопка “отправить”, а управляемый flow.

Этапы:

1. Пользователь открывает объект.
2. Нажимает `Apply`.
3. Система проверяет:
   - авторизован ли пользователь;
   - заполнен ли профиль;
   - загружены ли обязательные документы.
4. Если чего-то не хватает, показывает checklist.
5. Пользователь подтверждает заявку.
6. Создается `application`.
7. Пользователь видит статус и timeline.

Статусы MVP:

- `draft`
- `ready_to_submit`
- `submitted`
- `in_review`
- `viewing_invited`
- `rejected`
- `accepted`
- `withdrawn`

## 7. My Applications

Отдельный раздел кабинета.

Что должен показывать:

- список всех заявок;
- текущий статус;
- дату создания;
- связанный объект;
- краткий timeline;
- следующую рекомендацию.

Фильтры:

- active;
- archived;
- submitted;
- needs action.

## 8. Favorites

Минимальный список сохранённых объектов.

Нужно:

- сохранить объект;
- удалить из избранного;
- перейти к объекту;
- сразу начать заявку.

## 9. Saved Searches

Позволяет сохранять фильтры поиска.

Минимум:

- название поиска;
- параметры;
- включить/выключить уведомления;
- удалить поиск.

## 10. Documents

Отдельный экран лучше, чем прятать всё в Profile.

Что поддерживаем:

- загрузка файла;
- просмотр списка документов;
- статус:
  - uploaded;
  - missing;
  - expired;
  - verified.

## 11. Notifications

В MVP можно сделать простую in-app ленту:

- профиль неполный;
- заявка обновлена;
- найден подходящий объект;
- нужен новый документ.

Email-уведомления можно добавить как второй слой.

## Основные пользовательские потоки

## Поток 1. Новый пользователь

1. Sign up.
2. Email verify.
3. Onboarding.
4. Profile completion.
5. Search.
6. Save property or apply.

## Поток 2. Возвратный пользователь

1. Log in.
2. Dashboard.
3. View new matches or continue applications.

## Поток 3. Заявка на аренду

1. Открывает объект.
2. Нажимает `Apply`.
3. Видит checklist недостающих данных.
4. Дозаполняет профиль.
5. Подтверждает заявку.
6. Отслеживает status timeline.

## Поток 4. Сохранённый поиск

1. Настраивает фильтры.
2. Сохраняет поиск.
3. Получает новые результаты.
4. Сохраняет или открывает объекты.

## Как это ложится на текущий frontend

У тебя уже есть:

- `SearchPage`
- `AccountPage`
- auth pages

Поэтому рациональный путь:

- `SearchPage` превратить в реальный экран поиска с картой и фильтрами;
- `AccountPage` превратить в кабинет с вкладками:
  - Dashboard
  - Profile
  - Applications
  - Favorites
  - Saved Searches
  - Documents

Это позволит не ломать существующий роутинг, а постепенно заменить Framer-структуру рабочим продуктовым интерфейсом.

## Что важно не делать

- не смешивать профиль клиента и внутренний операторский интерфейс;
- не строить MVP вокруг automation-скриптов;
- не превращать `AccountPage` в одну длинную форму без навигации;
- не делать карту единственной точкой входа, список тоже обязателен;
- не завязывать отправку заявок на внешний UI-бот как на основную бизнес-функцию.

## Рекомендуемый MVP-результат

Если коротко, первый рабочий кабинет `bookimmo` должен дать пользователю три вещи:

- понятный поиск;
- сильный профиль арендатора;
- прозрачную воронку заявок.

Если эти три блока работают, дальше уже можно наращивать automation, matching и operator workflows.
