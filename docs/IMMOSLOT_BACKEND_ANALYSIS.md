# ImmoSlot Backend Analysis

## Что это такое

Текущий `backend/` в проекте `bookimmo` не является классическим веб-backend для клиентского кабинета.
Это Python-сервис автоматизации для поиска аренды на `ImmoScout24`, автозаполнения контактной формы через Chrome extension, логирования событий и уведомлений через Supabase и Telegram.

По сути это операционный сервис для внутренней работы одного оператора, а не многопользовательский API для клиентов.

## Общая схема работы

1. `monitor_with_extension.py` регулярно ищет новые квартиры через мобильный API `ImmoScout24`.
2. Параллельно `gmail_checker.py` читает Gmail и вытаскивает новые `expose_id` из email-уведомлений.
3. Найденные квартиры фильтруются по географии, комнатности, дубликатам и служебным правилам.
4. Скрипт открывает объявления в Chrome, где расширение `immoscout_contact_ext` автозаполняет и отправляет контактную форму.
5. Расширение сообщает локальному HTTP-серверу об успешной отправке или ошибке.
6. Сервис пишет события в Supabase/Postgres, может отправлять уведомления в Telegram и вести локальные логи.
7. Отдельные утилиты анализируют ответы из Gmail и качество конверсии.

## Главный файл

### `backend/monitor_with_extension.py`

Это центральный оркестратор всей системы.

Основные роли:

- опрашивает `ImmoScout24` API;
- принимает сигналы от Chrome extension на локальном HTTP-сервере;
- управляет очередью обработки квартир;
- получает контактные данные из БД;
- логирует успешные и неуспешные отправки;
- интегрируется с `supabase_db.py`, `telegram_bridge.py`, `gmail_checker.py`.

Ключевые части:

- Конфигурация:
  - список районов и геокодов Гамбурга;
  - интервалы опроса;
  - имена локальных файлов логирования;
  - глобальные очереди и in-memory дедупликация.
- Локальный HTTP-сервер на `0.0.0.0:5555`:
  - `GET /api/contact-data` возвращает данные клиента для заполнения формы;
  - `GET /api/server-url` возвращает URL локального сервера;
  - `GET /health` healthcheck;
  - `POST /contact_sent` фиксирует успешную отправку;
  - `POST /log_failure` фиксирует неуспешную отправку;
  - `POST /api/extension-heartbeat` подтверждает, что extension жив;
  - `POST /apartment/deleted` сообщает, что объявление удалено.
- Поиск квартир:
  - использует `https://api.mobile.immobilienscout24.de/search/list`;
  - фильтрует по районам, комнатам, дублям и исключениям;
  - найденные квартиры отправляет в очередь обработки.
- Работа с браузером:
  - открывает объявления в Chrome;
  - рассчитывает, что extension заполнит и отправит форму сам;
  - ждёт обратный сигнал от extension, а не симулирует форму на стороне Python.

Важно:

- В файле есть жёстко зашитые credentials и контактные данные.
- Архитектура ориентирована на одного профиля арендатора, а не на многих пользователей.
- Это stateful long-running process, а не REST API.

## Конфиг и секреты

### `backend/config.py`

Минимальный конфигурационный слой:

- читает `.env` без `python-dotenv`;
- поднимает настройки БД;
- поднимает настройки Supabase REST;
- поднимает Telegram и Gmail credentials.

Назначение файла:

- централизовать доступ к переменным окружения;
- позволить остальным модулям не знать, откуда пришли секреты.

Ограничение:

- не все модули реально используют этот слой последовательно;
- часть секретов всё ещё хардкодится напрямую в других файлах.

## Работа с базой и Supabase

### `backend/supabase_db.py`

Это слой доступа к данным.

Что делает:

- пишет отправленные контакты в `public.contacts`;
- проверяет, была ли уже отправка по `expose_id`;
- пишет квартиры в `apartments` через Supabase REST API;
- пишет timeline-события в `public.apartment_timeline`;
- получает историю событий по квартире.

Фактически файл совмещает два способа доступа:

- прямой PostgreSQL через `psycopg2`;
- REST-запросы в Supabase через `httpx`.

Сильная сторона:

- уже есть полезная модель timeline, которую можно переиспользовать в кабинете.

Слабые стороны:

- нет полноценного доменного слоя;
- нет явной схемы миграций;
- нет понятия `user`, `application`, `saved_search`, `tenant_profile`, `landlord_reply`;
- часть данных хранится как operational log, а не как нормализованная продуктовая модель.

## Telegram

### `backend/telegram_bridge.py`

Сервис отправки уведомлений и простого Telegram-бота.

Что умеет:

- рассылать события всем подписчикам;
- сообщать о найденной квартире;
- отправлять периодические отчёты;
- хранить локальный список подписчиков;
- хранить локальную историю сообщений.

Роль в архитектуре:

- это канал операторского мониторинга;
- для клиентского кабинета напрямую не нужен, но полезен как admin-notification layer.

Проблемы:

- токен бота захардкожен в коде;
- логика подписчиков хранится в локальном JSON;
- это не масштабируемый multi-tenant подход.

## Gmail-интеграция

### `backend/gmail_checker.py`

Парсер входящих email от `ImmoScout24`.

Что делает:

- ходит в Gmail через IMAP;
- ищет письма `Suchauftrag`;
- вытаскивает `expose_id`;
- пытается вытащить адрес;
- ведёт локальный cache уже обработанных писем.

Роль:

- второй источник новых квартир помимо API.

Практический смысл:

- если API не показывает объект сразу или отдаёт его иначе, письма могут помочь не пропустить объявление.

Ограничения:

- очень привязано к конкретной структуре писем;
- локальный state в `.gmail_seen_ids.json`;
- нет серверного persistence для inbox-processing state.

## Аналитика и служебные утилиты

### `backend/check_apartment.py`

Ручной диагностический скрипт.

Назначение:

- проверить, находится ли конкретная квартира в результатах поиска `ImmoScout24`;
- отладить фильтрацию по районам/комнатам.

### `backend/check_responses.py`

Аналитика воронки:

- ищет подтверждения отправки контактов в Gmail;
- ищет ответы от арендодателей;
- пытается сопоставить ответы с отправками;
- считает конверсию.

Это не backend-API, а offline analysis tool.

### Прочие файлы

- `analyze_email_responses.py` — дополнительные сценарии анализа ответов.
- `log_apartment.py` — служебное логирование.
- `restart_chrome_clean.py` — обслуживание браузера.
- `setup_chrome_cron.sh` — настройка cron для Chrome/автоматизации.
- `test_*.py` — ручные smoke/utility тесты, не полноценный тестовый контур.
- `ACTION_PLAN.md` — продуктово-операционный план `ImmoSlot`.
- `GMAIL_INTEGRATION_GUIDE.txt` — описание Gmail-потока.

## Chrome extension

### `backend/immoscout_contact_ext/manifest.json`

Расширение запускается на:

- страницах объявлений `expose`;
- страницах аккаунта;
- страницах messenger.

### `backend/immoscout_contact_ext/background.js`

Функции:

- загружает контактные данные с локального сервера;
- держит актуальный профиль контакта в `chrome.storage`;
- следит за доступностью `http://localhost:5555`;
- получает сообщения от content script.

### `backend/immoscout_contact_ext/content.js`

Функции:

- сообщает backend, что extension активен;
- определяет удалённые объявления;
- получает contact data;
- заполняет и отправляет форму контакта;
- шлёт сигнал о результате обратно на локальный Python-сервер.

Ключевая идея:

- бизнес-действие "отправить заявку" делается не через официальный API, а через UI-автоматизацию в браузере.

Это очень важно для будущего `bookimmo`:

- такой подход полезен для internal automation;
- он не подходит как основа клиентского кабинета, где пользователи должны работать через нормальный веб-интерфейс и серверный API.

## Где хранятся данные

Сейчас данные размазаны по нескольким слоям:

- Supabase Postgres:
  - контакты;
  - timeline событий;
  - часть квартир;
  - пользовательские сообщения.
- локальные JSON/JSONL:
  - кэш уже обработанных email;
  - история найденных/обработанных квартир;
  - локальные подписчики Telegram;
  - служебные логи.
- Gmail:
  - источник входящих уведомлений и ответов.
- Chrome storage:
  - временное хранение contact data в extension.

Вывод:

- storage слой сейчас гибридный и операторский;
- для SaaS-кабинета его нужно нормализовать.

## Архитектурная оценка

### Что в текущем backend уже полезно

- логика работы с `ImmoScout24`;
- понимание жизненного цикла заявки;
- `timeline` модель событий;
- интеграция с Supabase;
- проверенные фильтры по рынку и району;
- operational know-how по аренде в Германии.

### Что не подходит для кабинета клиентов в текущем виде

- нет REST API или GraphQL API для frontend;
- нет multi-user модели;
- нет аутентификации клиентов;
- нет профилей арендаторов;
- нет сохранённых поисков;
- нет карты и гео-поиска для клиента;
- нет объектной модели заявок и статусов в продуктовой форме;
- нет очереди фоновых jobs как отдельного уровня;
- нет разделения internal automation и client-facing backend.

### Главные риски

- секреты лежат в коде и `.env`;
- сильная привязка к одному клиенту;
- зависимость от UI `ImmoScout24`, который может поменяться;
- локальный state делает воспроизводимость слабой;
- Python service и extension работают как long-running bot, а не как масштабируемый backend.

## Что это значит для кабинета клиентов `bookimmo`

Пользовательская цель:

- клиент видит карту;
- делает поиск;
- размещает заявку на аренду;
- заполняет профиль максимально полно;
- далее может отслеживать активность и ответы.

Для этого нужен уже другой backend-контур.

### Что можно переиспользовать

- идеи фильтрации квартир;
- поля contact/application timeline;
- Supabase как базу данных и auth;
- knowledge о жизненном цикле аренды;
- часть логики импорта объектов, если мы захотим internal ingestion pipeline.

### Что нужно строить отдельно

- client-facing API;
- сущности пользователей и ролей;
- профиль арендатора;
- поиск и карта;
- модель заявок на аренду;
- модель документов;
- трекинг статусов;
- админка/операторка отдельно от клиентского кабинета.

## Рекомендуемая новая модель для `bookimmo`

### Frontend

Текущий React/Vite frontend можно расширять под кабинет.

Новые ключевые разделы:

- карта с объектами;
- поисковый экран;
- профиль клиента;
- мои заявки;
- документы;
- уведомления;
- избранное;
- история коммуникаций.

### Backend

Нужен отдельный app-backend, а не развитие текущего automation script как есть.

Минимальные сущности:

- `users`
- `tenant_profiles`
- `rental_requests`
- `saved_searches`
- `properties`
- `property_locations`
- `applications`
- `application_events`
- `documents`
- `messages`
- `favorites`

### Важное разделение

Нужно развести два слоя:

1. `client platform`
   - кабинет клиентов;
   - поиск, карта, профили, заявки;
   - безопасная auth-модель.

2. `internal automation`
   - ingestion квартир;
   - интеграция с внешними площадками;
   - расширения, боты, Gmail, Telegram;
   - фоновые jobs для операторов.

Их можно связать общей БД и очередями, но не смешивать в один процесс.

## Практический вывод

Текущий `backend/` лучше считать не будущим backend кабинета, а отдельным internal ingestion/automation service.

Для кабинета `bookimmo` правильнее:

- оставить этот код как источник экспертизы и, возможно, как private automation worker;
- спроектировать новый backend/API под пользователей;
- постепенно переиспользовать только полезные доменные куски.

## Что делать дальше

Логичный следующий шаг для `bookimmo`:

1. Спроектировать data model кабинета клиентов.
2. Определить MVP экранов: карта, поиск, профиль, заявка.
3. Выбрать backend-стек:
   - Supabase-first;
   - или отдельный Node/Python API поверх Supabase/Postgres.
4. Развести `client app` и `automation worker`.
5. После этого уже строить UI и реальные API-контракты.

## Короткий итог в одной фразе

`backend/` сейчас делает не "кабинет клиентов", а "автоматизированную операционную систему подачи заявок на аренду"; для `bookimmo` его нужно не просто доработать, а архитектурно отделить от нового клиентского backend.
